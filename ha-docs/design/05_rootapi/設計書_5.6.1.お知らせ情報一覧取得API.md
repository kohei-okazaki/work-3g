# 設計書 5.6.1. お知らせ情報一覧取得API

## 1. 機能概要

- 未削除のお知らせ情報をページ単位で検索し、各お知らせの本文JSONをS3から読み込んで返す。
- 入出力の機械可読定義は[OpenAPI入出力仕様](./openapi.yaml)の`rootListNews`を参照する。


## 4. 処理フロー

```mermaid
flowchart TD
    N1["1. お知らせ一覧要求の受付"]
    N2{"2. 検索条件の確認"}
    N3["3. お知らせ一覧の取得"]
    N4["4. お知らせ本文の取得"]
    N5["5. 一覧結果の返却"]
    N6["6. 異常結果の返却"]
    N1 --> N2
    N2 -->|正常| N3
    N2 -->|入力不正| N6
    N3 --> N4
    N3 -->|異常| N6
    N4 --> N5
    N4 -->|異常| N6
    N5 --> End(["終了"])
    N6 --> End
```

| 処理順 | 処理概要 | 処理詳細 | 関連項番 |
| --- | --- | --- | --- |
| 1 | お知らせ一覧要求の受付 | Bearer認証を経て一覧要求を受け付ける。認証不成立はフィルター側で終了する。 | 4.1.1 |
| 2 | 検索条件の確認 | pageを変換・検証し、ページ条件を作成する。不正なら一覧検索へ進まない。 | 4.1.2、4.3.1 |
| 3 | お知らせ一覧の取得 | 未削除のお知らせをID降順で要求ページ分取得する。0件も正常な空一覧として扱う。 | 4.2.1、4.3.1 |
| 4 | お知らせ本文の取得 | 各お知らせのS3キーで本文JSONを取得し、DBの情報と合わせて本文・タグを編集する。取得・解析失敗は一覧全体の異常とする。 | 4.4、4.3.1 |
| 5 | 一覧結果の返却 | 未削除件数からページングを作成し、news_listとともにHTTP 200で返す。範囲外ページは補正しない。 | 4.3.2 |
| 6 | 異常結果の返却 | 入力不正・DBや本文の取得失敗は共通処理の異常応答で終了する。一部だけ取得できた一覧は返さない。 | 4.1.3、4.3、4.4 |

### 4.1. 入力チェック

#### 4.1.1. 認証・利用範囲の確認

| 対象 | ルール | 検証メッセージ・失敗時 |
| --- | --- | --- |
| 認証 | Authorization: Bearer <JWT>で署名とsubjectを検証する。除外URLではないため認証が必要。 | フィルタの共通処理。コントローラのerrors形式は保証しない。 |
| 利用対象 | JWT認証後にこの操作固有のロール別権限検査や、JWTのsubjectと対象ユーザIDを照合する処理は設けない。 | - |

#### 4.1.2. 入力項目・補完条件の確認

| 対象 | ルール | 検証メッセージ・失敗時 |
| --- | --- | --- |
| page | 省略時0。0始まり。Integerへ変換後、@Decimalで0以上999999999以下（両端含む）を検証する。 | page is positive |

#### 4.1.3. 入力異常時の扱い

要求DTOに追加の検索項目はない。

| 発生条件 | HTTPステータス | 扱い |
| --- | --- | --- |
| Bean Validation | 400 | errors配列に各検証メッセージを設定する。 |
| パス・クエリの型変換 | 400 | <項目名> is type error. value=<入力値>。 |
| JSONの数値・日付変換 | 400または500 | HttpMessageNotReadableExceptionの原因が対象のInvalidFormatExceptionなら400。日付はdate format error. Please use yyyy/MM/dd.、数値はnumber format error. Please use numeric value.。その他は500・unexpected error.。 |
| 認証フィルタ・共通HTTP処理 | 共通処理に従う | 上記のresult/errors形式とは別に扱う。401と固定JSONへ一律に統一する実装はない。 |

入力・認証の例外がコントローラの例外ハンドラーに到達した場合は、ログ出力とROOT向けSlackエラー通知を行う。認証フィルタの例外は同じJSON形式に統一されない。

### 4.2. DB操作
#### 4.2.1. 一覧・件数検索

```sql
SELECT
    *
FROM
    NEWS_INFO
WHERE
    DELETE_FLAG = FALSE
ORDER BY
    SEQ_NEWS_INFO_ID DESC
LIMIT
    :offset
    , :page_size;

SELECT
    COUNT(*)
FROM
    NEWS_INFO
WHERE
    DELETE_FLAG = FALSE;
```

| 項目 | 設定値 | 備考 |
| --- | --- | --- |
| `:offset` | 要求の`page` × `front.news.page` | 0始まりの要求ページから`Pageable.getOffset()`を算出する。 |
| `:page_size` | 設定`front.news.page`の1ページ件数 | `Pageable.getPageSize()`を取得し、LIMITへ設定する。 |

### 4.3. 業務処理・応答編集

#### 4.3.1. 一覧の取得・応答項目の編集

| 順序 | 処理 | 内容 |
| --- | --- | --- |
| 1 | ページ条件作成 | pageとfront.news.pageからPageableを作成する。 |
| 2 | DB検索 | NEWS_INFOのDELETE_FLAG=falseを条件に、SEQ_NEWS_INFO_ID降順で検索する。 |
| 3 | S3取得・応答編集 | 各行のS3_KEYでJSONを読み込み、title/date/detail/tagを取得する。IDと登録・更新日時はDBの値を設定する。 |

#### 4.3.2. 総件数取得・ページング・返却

| 順序 | 処理 | 内容 |
| --- | --- | --- |
| 1 | 件数・応答 | 未削除のNEWS_INFOを数え、news_listとnews?pageを基準とするpagingを返す。 |

1ページ件数は`front.news.page`から取得する。SQLのOFFSETは`page × page_size`とし、要求ページを実在範囲へ補正しない。範囲外なら一覧は空になる。`PagingViewFactory`は`news?page=<page>`のリンクを作成する。総件数0または範囲外では表示範囲を0〜0とする。

| 項目群 | 型 | 内容 |
| --- | --- | --- |
| total_record_num/from_record_num/to_record_num/total_page | integer | 総件数・先頭/末尾の表示番号・総ページ数。 |
| current_page_num/record_per_page | integer | 0始まりの要求ページと1ページ件数。 |
| can_go_next/can_go_previous/can_go_last/can_go_first | boolean | 各方向へ移動できるかを示す。 |
| next_href/previous_href/last_href/first_href | string | 対応ページへのリンク。移動不可時も値は設定する。 |

| 発生条件 | HTTPステータス | 扱い |
| --- | --- | --- |
| 予期しない例外 | 500 | unexpected error.。不正JSONを常に400へ変換する実装ではない。 |

異常応答の基本形は`{"result":"1","errors":[{"message":"..."}]}`とする。正常応答はHTTP 200。例外ハンドラーはログ出力とROOT向けSlackエラー通知を行う。DB検索・更新や外部サービスの詳細はサーバ側の例外として扱う。エラー応答には内部エラーコードを設定しない。

**SQL呼び出し時の結果・例外の扱い**

`NewsInfoSearchService.findAll`と`countBySeqNewsInfoId(null)`を使用する。

| 発生条件 | HTTPステータス | 扱い |
| --- | --- | --- |
| BaseException | 500 | application error.。内部のBE/CE等のコードや詳細をそのままJSONへ出力しない。 |

DB検索・更新で予期しない例外が発生した場合はHTTP 500、`unexpected error.`とする。例外ハンドラーはログとROOT向けSlackエラー通知を行う。

### 4.4. S3読み込み

DBの`S3_KEY`をそのままキーとして、設定バケットから`AwsS3Component.getS3ObjectByKey`で取得する。JSONを`NewsDto`へ変換し、タグの色・名前を個別にコピーする。1件のS3取得・解析が失敗した場合にその行だけを除外する処理はなく、要求全体が例外となる。DB・S3を更新しない。

| 発生条件 | HTTPステータス | 扱い |
| --- | --- | --- |
| BaseException | 500 | application error.。内部のBE/CE等のコードや詳細をそのままJSONへ出力しない。 |

S3取得・JSON変換・アップロード・削除などで発生したBaseExceptionはHTTP 500、`application error.`、それ以外の予期しない例外はHTTP 500、`unexpected error.`とする。例外ハンドラーへ到達した場合はログとROOT向けSlackエラー通知を行う。
